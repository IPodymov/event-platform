# Турнирная платформа — инструкции для Claude Code

Ты ведёшь разработку веб-платформы киберспортивных турниров на Django. Этот файл — главный источник требований. Полный план спринтов лежит в `docs/tournament_platform_plan.md` и `docs/tournament_sprints_tasks.csv`. Если что-то в задаче противоречит этому файлу или неоднозначно, остановись и спроси, а не додумывай.

## 1. Продукт в двух словах
- Организаторы создают турниры, игроки и команды регистрируются, проходят check-in, играют матчи по сетке и отправляют результаты.
- Дисциплины MVP: **CS2**, **Dota 2**, **LoL: Wild Rift** (команды 5 + до 2 запасных) и **Hearthstone** (соло 1v1).
- Пользователи донатят на платформу. Из общего банка и целевых донатов формируются призовые фонды турниров, которые выплачиваются победителям.

## 2. Стек и соглашения
- Python 3.12, Django 5.x, DRF, PostgreSQL 16, Redis, Celery + Celery Beat, Django Channels, django-allauth, drf-spectacular.
- Frontend MVP: Django Templates + HTMX + Alpine.js. Вся бизнес-логика доступна и через REST API.
- Docker + docker-compose (сервисы: `web`, `db`, `redis`, `worker`, `beat`).
- Качество: `ruff` (lint + format), `mypy` (strict для `brackets`, `matches`, `payments`, `prizes`), `pytest`, `pytest-django`, `factory_boy`, `hypothesis`.
- Код, имена и комментарии в коде — на английском. UI-строки через `gettext`, язык по умолчанию — русский.
- Бизнес-логика живёт в **сервисном слое** (`services.py` / `services/`), а не во views, формах, сериализаторах или `save()`. Views тонкие.
- Чтения сложных выборок — в `selectors.py`.
- Любое изменение, затрагивающее несколько записей (продвижение по сетке, проводки, выплаты), выполняется в `transaction.atomic()` с `select_for_update()` на изменяемых строках.
- Время хранится в UTC (`USE_TZ=True`). Пользователю показывается в его часовом поясе из профиля.
- Статусы — через `models.TextChoices`. Переходы статусов — только через сервисные функции, которые проверяют допустимость перехода и бросают доменное исключение.

## 3. Порядок работы
1. Работай строго по одной задаче из CSV за раз, в порядке спринтов.
2. Перед кодом коротко опиши план: какие файлы, модели, миграции.
3. Для `brackets`, `matches`, `payments`, `prizes` сначала пиши тесты, потом реализацию.
4. После каждой задачи: `ruff check`, `ruff format`, `mypy`, `pytest`. Не помечай задачу готовой, пока всё не зелёное.
5. Один логический коммит на задачу, сообщение в стиле Conventional Commits (`feat(brackets): ...`).
6. Не добавляй зависимости без объяснения, зачем они нужны.
7. Никогда не коммить секреты. Все ключи — через переменные окружения, с примером в `.env.example`.

## 5. Ключевые модели (минимум полей)
- **User**: кастомная модель на `AbstractUser`, `USERNAME_FIELD = "email"`. Создаётся до первой миграции.
- **Profile**: `nickname` (уникальный), `avatar`, `country`, `timezone`.
- **GameAccount**: `user`, `game`, `external_id` (Steam ID64 / Riot ID / BattleTag), `region`, `verified`. Уникальность: `(game, external_id)`.
- **Game**: `slug` (`cs2`, `dota2`, `wildrift`, `hearthstone`), `participant_type` (`solo` / `team`), `roster_size`, `max_substitutes`, `allowed_series` (Bo1/Bo3/Bo5), `result_verification` (`manual` / `opendota`).
- **Team**: `name`, `tag`, `logo`, `game`, `captain`. Один игрок — максимум одна активная команда на дисциплину.
- **TeamMembership**: `team`, `user`, `role` (`captain` / `player` / `substitute`), `joined_at`, `left_at`.
- **Tournament**: `game`, `organizer`, `title`, `rules`, `region`, `max_participants`, `series_format`, `registration_opens_at`, `registration_closes_at`, `checkin_opens_at`, `starts_at`, `status`.
- **Stage**: `tournament`, `order`, `format` (`single_elim` / `double_elim` / `round_robin` / `swiss`), `settings` (JSON: размер групп, число выходящих, Bo для финалов и т.п.).
- **Registration**: `tournament`, `team` *или* `user` (ровно одно, через `CheckConstraint`), `roster_snapshot` (JSON-состав на момент регистрации), `seed`, `status`.
- **Match**: `stage`, `round`, `position`, `bracket_side` (`upper` / `lower` / `grand_final` / `group` / `swiss`), `participant_a`, `participant_b` (FK на Registration, nullable), `best_of`, `scheduled_at`, `status`, `winner`, `next_match_winner`, `next_match_winner_slot`, `next_match_loser`, `next_match_loser_slot`.
- **MatchGame**: `match`, `number`, `map` (CS2), `winner`, `external_match_id` (Dota 2), `deck_class` (HS).
- **MatchReport**, **Dispute** — см. раздел 8.
- Деньги — см. раздел 11.

## 6. Жизненный цикл турнира
```
draft → registration_open → registration_closed → checkin → in_progress → completed
                                   ↘ cancelled (из любого статуса до completed)
```
- Переходы по времени выполняют периодические задачи Celery Beat (раз в минуту). Задачи идемпотентны.
- **Регистрация**:
  - командная: подаёт капитан; в составе `roster_size` основных и до `max_substitutes` запасных;
  - у каждого игрока должен быть `GameAccount` нужной игры и региона турнира;
  - ни один игрок не может состоять в двух зарегистрированных составах одного турнира;
  - состав фиксируется в `roster_snapshot`;
  - при заполнении лимита новые регистрации попадают в лист ожидания (`waitlisted`).
- **Регистрация никогда не зависит от донатов.** Нельзя добавлять проверку оплаты или доната как условие участия.
- **Check-in**: окно с `checkin_opens_at` до `starts_at`. Отмечается капитан или соло-игрок. В момент старта неотметившиеся переводятся в `no_show`, освободившиеся места заполняются из листа ожидания (по времени регистрации), после чего генерируется сетка.
- Если участников после check-in меньше 2, турнир отменяется.

## 7. Сетки (`apps/brackets`)
Общий интерфейс:
```python
class BracketGenerator(Protocol):
    def generate(self, stage: Stage, participants: list[Registration]) -> list[Match]: ...
```
Генератор создаёт все матчи этапа сразу (кроме Swiss) и связывает их через `next_match_*`. Матчи без соперников создаются с пустыми слотами.

**Посев.** Режимы `random`, `manual`, `rating`. Пары в первом раунде расставляются по стандартному порядку посева (1–N, 2–(N−1)… с рекурсивным размещением, чтобы 1 и 2 сеяные встретились только в финале).

**Single Elimination.**
- Размер сетки — ближайшая степень двойки `S ≥ N`. Число bye: `S − N`, достаются лучшим сеяным.
- Матч с bye сразу получает статус `completed`, победитель продвигается без счёта.
- Опционально матч за 3-е место (`settings.third_place_match`).

**Double Elimination.**
- Верхняя сетка = Single Elimination.
- Проигравший в верхнем раунде `r` падает в нижнюю сетку. Нижняя сетка чередует раунды «сведения» (выжившие нижней сетки против выпавших из верхней) и «внутренние» раунды. Чтобы избежать быстрых повторных встреч, порядок выпадающих в нижнюю сетку разворачивается через раунд.
- Гранд-финал: победитель верхней против победителя нижней. Если `settings.bracket_reset = true` и побеждает участник из нижней сетки, создаётся второй (решающий) матч гранд-финала.
- Bye в нижней сетке обрабатываются так же автоматическим продвижением.
- Обязательные тесты: для N от 2 до 64 — у каждого участника, кроме чемпиона, ровно 2 поражения (с учётом bye), у чемпиона не больше 1, нет «висящих» матчей.

**Round Robin.**
- Круговая система методом Бергера (circle method), для нечётного N — фиктивный bye.
- Поддержка групп: `settings.group_count`, распределение «змейкой» по посеву.
- Очки: победа 3, поражение 0 (ничья — только если Bo2, тогда 1).
- Тай-брейки по порядку: очки → личная встреча (среди равных) → разница карт/игр → разница раундов (только CS2) → дополнительный матч, назначаемый организатором.
- Из группы выходят `settings.advance_count` лучших в следующий этап.

**Swiss (в первую очередь для CS2).**
- Раунды генерируются по одному, после завершения предыдущего.
- Пары внутри групп с одинаковым счётом (W-L). Повторные встречи запрещены. Если пару без повтора составить нельзя — опускай участника в соседнюю группу счёта.
- Внутри группы пары формируются по Buchholz (сумма побед соперников), затем по посеву.
- Выход при 3 победах, вылет при 3 поражениях (настраивается). Матчи, решающие выход или вылет, играются в Bo3, остальные в Bo1 (настраивается).
- Обязательные тесты (`hypothesis`): нет повторных встреч, у каждого участника в итоге ровно `win_target` побед или `loss_target` поражений.

**Продвижение.** Функция `advance_match(match)`:
- вызывается только после подтверждения результата;
- в одной транзакции с `select_for_update()` записывает победителя в слот `next_match_winner_slot`, проигравшего — в `next_match_loser_slot`;
- если следующий матч оказался с bye — продвигает рекурсивно;
- если это был последний матч этапа — запускает подведение итогов этапа и, если нужно, следующий этап или завершение турнира.

## 8. Матчи и результаты
Статусы матча:
```
pending (нет соперников) → scheduled → ready (оба отметились / время наступило)
  → in_progress → awaiting_confirmation → completed
                         ↘ disputed → completed
  → forfeit (техническое поражение)
```
- **Отчёт** подаёт капитан (или соло-игрок) любой стороны: счёт по каждой игре серии и до 5 скриншотов (S3, только изображения, до 5 МБ каждый).
- Валидация серии: в Bo3 победа при 2 выигранных играх, в Bo5 — при 3; лишних игр после победы нет; ничьих нет.
- **Подтверждение**: вторая сторона подтверждает или открывает спор. Без реакции в течение `RESULT_AUTO_CONFIRM_MINUTES` (по умолчанию 30) результат подтверждается автоматически задачей Celery.
- Если обе стороны прислали противоречащие отчёты — матч автоматически уходит в `disputed`.
- **Спор**: обе стороны прикладывают доказательства, модератор выносит решение (выбирает отчёт или вводит свой счёт). Решение логируется в `AuditLog`.
- **Неявка**: если сторона не отметилась на матч в течение `NO_SHOW_MINUTES` (по умолчанию 15) после `scheduled_at`, ей присуждается техническое поражение. Если не явились обе — организатор решает вручную.
- Все изменения результатов после `completed` разрешены только организатору и модератору, с записью в `AuditLog` и пересчётом зависимых матчей (если зависимые уже сыграны — запрет и предупреждение).

## 9. Особенности дисциплин
**CS2 — map veto.**
- Пул карт берётся из активного `MapPool` (7 карт). Первым банит участник с более высоким посевом (настраивается: монетка).
- Bo1: бан, бан, бан, бан, бан, бан → оставшаяся карта; сторону выбирает тот, кто не делал последний бан.
- Bo3: бан, бан, пик, пик, бан, бан → оставшаяся карта — десайдер. Сторону на карте выбирает соперник того, кто её пикнул.
- Bo5: бан, бан, пик, пик, пик, пик → оставшаяся карта — десайдер.
- Veto идёт в реальном времени через WebSocket, на ход даётся `VETO_TURN_SECONDS` (по умолчанию 60). При таймауте — случайный бан/пик за участника.

**Dota 2 — автопроверка.**
- В отчёте по каждой игре указывается Match ID.
- Адаптер OpenDota получает матч и проверяет: игроки — это Steam ID из `roster_snapshot` (допускается замена запасным из того же состава), матч сыгран после `scheduled_at`, определяет победителя.
- Если проверка прошла — результат подтверждается без ожидания соперника. Если API недоступен — ретраи с экспоненциальной задержкой, затем откат на ручное подтверждение.

**Hearthstone.**
- До закрытия регистрации игрок подаёт `deck_count` колод (deck codes) разных классов. Колоды декодируются и валидируются, скрыты от соперников до старта турнира.
- Опционально бан одного класса соперника перед матчем.
- **Conquest**: чтобы выиграть серию, нужно победить каждой своей колодой по разу; выигравшая колода дальше не используется.
- **Last Hero Standing**: проигравшая колода выбывает; выигрывает тот, у кого осталась хотя бы одна колода.
- Валидация отчёта учитывает выбранный формат.

**Wild Rift.**
- Только ручной режим: отчёт + скриншоты + подтверждение соперника.
- Турнир привязан к региону сервера; Riot ID всех игроков должен быть этого региона.

## 10. Права доступа
- Роли на уровне платформы: `user`, `moderator`, `admin`.
- Роли на уровне турнира: `organizer`, `co_organizer`.
- Управлять турниром могут только его организаторы и админы. Разрешать споры — организаторы, модераторы и админы. Финансовые операции (распределение банка, подтверждение выплат) — только `admin`.
- Проверки прав — в сервисах и в DRF permission-классах, не только в шаблонах.

## 11. Деньги (`apps/payments`, `apps/prizes`)
**Общие правила.**
- Все суммы хранятся целыми числами в минимальных единицах валюты (копейки) в `BigIntegerField`. Никаких `float`. Для процентов — `Decimal` с явным округлением `ROUND_HALF_UP`.
- Балансы **не хранятся** в отдельных полях как источник истины: они вычисляются как сумма проводок в журнале. Допускается кэшированный баланс, который пересчитывается и сверяется.
- Проводки неизменяемы: исправление — только сторнирующей проводкой.

**Журнал (двойная запись).**
- `LedgerAccount`: `code` (`provider_clearing`, `platform_bank`, `platform_commission`, `tournament_pool:<id>`, `payouts_pending`, `payouts_paid`, `refunds`), `currency`.
- `LedgerTransaction`: `type`, `reference` (донат / выделение / выплата), `created_at`, `created_by`.
- `LedgerEntry`: `transaction`, `account`, `amount` (положительное — дебет, отрицательное — кредит). Сумма записей транзакции всегда равна 0 — проверять в сервисе и тестами.

**Донат.**
1. Пользователь выбирает сумму (не меньше `MIN_DONATION`) и назначение: общий банк или конкретный турнир (только если его фонд ещё не зафиксирован). Можно отметить «анонимно».
2. Создаётся `Donation(status=pending)` и платёж у провайдера с `idempotence_key = donation.id`.
3. Статус меняется **только по вебхуку** провайдера (подпись и IP проверяются) или по сверке через API — не по редиректу пользователя.
4. Обработка вебхука идемпотентна (уникальный `provider_payment_id`); повторный вебхук ничего не меняет.
5. При `succeeded` в одной транзакции создаются проводки: всё поступление на `provider_clearing` → комиссия `PLATFORM_COMMISSION_PERCENT` на `platform_commission` → остаток на `platform_bank` или `tournament_pool:<id>`.
6. Провайдеры подключаются через интерфейс `PaymentProvider` (`create_payment`, `parse_webhook`, `refund`, `get_payment`). Первая реализация — ЮKassa, затем Stripe.

**Распределение банка.**
- Админ выделяет деньги из `platform_bank` в фонд турнира вручную или правилом (фиксированная сумма / процент от банка). Нельзя выделить больше текущего баланса банка.
- Каждое выделение — `Allocation` + проводка.

**Призовой фонд.**
- `PrizePool`: `tournament`, `target_amount` (опционально, для прогресс-бара), `status` (`collecting` → `locked` → `distributed` → `paid` | `refunded`).
- При старте турнира фонд переходит в `locked`, дальнейшие целевые донаты в этот турнир отклоняются (пользователю предлагается общий банк).
- `PrizePlace`: место и доля в процентах; сумма долей = 100. Шаблоны: `100`, `60/40`, `50/30/20`, `40/25/15/10/5/5`, плюс произвольная схема.
- Расчёт сумм: доля × фонд с округлением вниз до копейки; остаток от округления добавляется к 1-му месту.
- Командный приз по умолчанию делится поровну между игроками `roster_snapshot` (основные + запасные, сыгравшие хотя бы одну игру), остаток от деления — капитану. Капитан может до выплат задать другое распределение, которое подтверждает каждый игрок.

**Выплаты.**
- После `completed` турнира создаются `Payout` для каждого получателя со статусом `awaiting_details`.
- Получатель вводит реквизиты и проходит верификацию (`kyc_status`). Реквизиты хранятся зашифрованными (поле с шифрованием, ключ из окружения), в логах и в админке — маскированы.
- Статусы: `awaiting_details → pending_review → approved → sent → paid` | `failed` | `cancelled`. Подтверждает только `admin`, каждое действие — в `AuditLog`.
- Проводки: `tournament_pool:<id>` → `payouts_pending` при `approved`, `payouts_pending` → `payouts_paid` при `paid`.
- Поле `tax_withheld` предусмотреть сразу; логику удержания НДФЛ реализовать после юридической консультации (до неё — флаг-заглушка и TODO).

**Отмена турнира.**
- Целевые донаты в отменённый турнир по выбору админа: возврат через провайдера или перевод в `platform_bank` (по умолчанию — перевод в банк, если оферта это допускает). Выделенные из банка деньги возвращаются в `platform_bank`.

**Тесты денежной логики (покрытие не ниже 95%).**
- Сумма проводок любой транзакции = 0.
- Повторный вебхук не создаёт новых проводок.
- Параллельные донаты и выделения не приводят к отрицательному балансу банка (тест с конкурентными транзакциями).
- Распределение призов: сумма выплат точно равна фонду для любых долей и сумм (`hypothesis`).

## 12. Уведомления и realtime
- События домена (`match_ready`, `result_reported`, `dispute_opened`, `checkin_opened`, `donation_received`, `payout_status_changed`) публикуются через одну функцию `notify(event, recipients, payload)`, которая раскладывает их по каналам: in-app, email, Telegram/Discord (по настройкам пользователя).
- WebSocket-группы: `tournament_<id>` (сетка, призовой фонд), `match_<id>` (счёт, veto).
- Отправка уведомлений — только в Celery-задачах после коммита транзакции (`transaction.on_commit`).

## 13. Безопасность
- Rate limiting на логин, регистрацию, отчёты, донаты.
- Загрузки: проверка MIME и размера, перекодирование изображений, хранение вне веб-корня.
- CSRF везде, CSP, `SECURE_*` настройки в prod.
- Все действия организаторов, модераторов и админов с результатами, участниками и деньгами пишутся в `AuditLog` (кто, что, когда, было/стало).
